# 0006. 同期では「操作（コマンド）」を送り、サーバーで同じユースケースを再実行する

- ステータス: 提案
- 日付: 2026-10-05
- 関連: ADR 0002 の決定 3・4（Outbox に記録する内容とサーバーでの検証方法）を置き換える

## コンテキスト

- ADR 0002 では、Outbox に「ドメインイベント + 変更後の値 + 基準 version」を記録し、サーバーが同じドメインコードで検証するとしていた
- 「変更後の値」を受け取る方式では、値が正しい遷移の結果かを検証する処理をサーバー側に別途用意する必要がある
- ドメインとユースケースはクライアント・サーバーで共有している（ADR 0001）

## 決定

1. Outbox には **操作（`TaskCommand`）** を記録する
   - 例: `{ type: "CreateTask", id, title }`、`{ type: "ChangeTaskStatus", id, action }`
   - 各変更には **`changeId`**（クライアント生成）を付け、`PendingChange` として送る
2. サーバーは push された操作を、送られた順に **既存のユースケース（`CreateTask` / `ChangeTaskStatus`）で再実行** する
   - ドメインのルールに反する操作は `rejected` として結果を返し、後続の操作の処理は続ける
   - 例: 別端末で完了済みのタスクに「着手」を送ると、状態遷移ルールにより `InvalidStatusTransition` で差し戻される
3. サーバーは **処理済みの `changeId` と結果を記録** し、同じ `changeId` の再送には再実行せず前回の結果を返す（応答の喪失による再送対策）
4. pull はサーバーの変更ログを `seq`（単調増加の連番）順に返す。クライアントは `cursor` を保存し、続きがあれば繰り返し取得する
5. 同期の取り決め（型・ユースケース）は `packages/sync` に置く

### API

| エンドポイント                        | 内容                                                                                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/sync/push`                 | `{ changes: PendingChange[] }`（最大 100 件）→ `{ results: ChangeResult[] }`。ドメインのルール違反も 200 で返し、結果の中で `rejected` とする |
| `GET /api/sync/pull?cursor=N&limit=M` | `{ changes: { seq, task }[], cursor, hasMore }`（`limit` は最大 500）                                                                         |

## 結果

- 良い点: サーバーの検証は既存のユースケースを呼ぶだけで済み、クライアントと完全に同じルールが適用される
- 良い点: 操作の意図（「完了した」）が残るため、競合時に「どの操作が差し戻されたか」を利用者に示しやすい
- 悪い点: 新しい操作を追加するたびに `TaskCommand` と push の入力検証に追加が必要
- 留意点: 処理済み記録とユースケースの保存は、PostgreSQL 実装では同一トランザクションにする必要がある（メモリ実装では未対応）
- 留意点: タイトル・期限などの項目編集を追加する際は、項目単位の LWW（ADR 0002 決定 6）を操作の適用ルールとして別途定める
