# 0004. 入力解析を差し替え可能な Port とする

- ステータス: 提案
- 日付: 2026-10-05

## コンテキスト

- 将来、音声入力と、入力文から期限・優先度を自動抽出する機能（LLM 利用）を提供したい
- ただし MVP には含めず、後付けとする
- 解析は外部サービスに依存し、オフライン時は利用できない
- 入力の手軽さを損なわないことが最重要

## 決定

1. Capture コンテキストに **`TaskDraftParser` Port** を定義する

```ts
interface TaskDraftParser {
  parse(input: RawInput, context: ParseContext): Promise<Result<ParsedTaskAttributes, ParseError>>;
}
```

- `ParseContext` は現在日時・タイムゾーンなど、相対表現（「明日」等）の解決に必要な情報を持つ

2. **入力はまず `TaskDraft`（未解析）として保存** し、解析後に `Task` へ確定する
   - オフライン時は `pending` のまま保存され、オンライン復帰後に解析する
   - 解析失敗時は原文をタイトルとして `Task` 化できる
3. 実装は段階的に差し替える

| 段階         | 実装                                              | 動作環境                     |
| ------------ | ------------------------------------------------- | ---------------------------- |
| v1（MVP）    | `PassthroughParser`: 原文をそのままタイトルにする | クライアント（オフライン可） |
| v1.5（任意） | `RuleBasedParser`: 「明日」「至急」等の簡易抽出   | クライアント（オフライン可） |
| v2           | `LlmParser`: LLM で期限・優先度を抽出             | サーバー（Adapter）          |

4. **外部サービスの型をドメインに持ち込まない**（腐敗防止層）。LLM の応答は Adapter 内で `ParsedTaskAttributes` に変換・検証する
5. 音声認識（文字起こし）も Port（`SpeechRecognizer`）とし、プラットフォームごとに Adapter を用意する

## 結果

- 良い点: MVP では解析なしで素早く提供でき、後から解析器を差し替えるだけで機能を追加できる
- 悪い点: `TaskDraft` → `Task` の 2 段階になるため、MVP 時点ではやや冗長
  - MVP では `PassthroughParser` により即時確定させ、利用者からは 1 段階に見えるようにする

## 要確認事項

- LLM 利用時の送信データ（利用者の入力原文）の取り扱い方針・保持期間・利用規約は、v2 着手時に確認する
- 利用する LLM・音声認識サービスの選定は v2 着手時に行う。料金・仕様は導入時点の公式情報で確認する
