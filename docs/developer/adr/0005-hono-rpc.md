# 0005. API は TypeScript（Hono）とし、型は Hono RPC で共有する

- ステータス: 提案
- 日付: 2026-10-05

## コンテキスト

- ADR 0001 で、API の取り決め（スキーマ）の共有方法は実装着手時に OpenAPI か型共有 RPC かを選ぶとしていた
- API を Python（FastAPI 等）で別実装する案も検討した
- オフライン同期では、クライアントの変更をサーバーが同じドメインコードで再検証する（ADR 0002）
- 現時点で想定するクライアント（Web / Expo / Tauri）はすべて TypeScript

## 決定

1. API サーバーは **TypeScript + Hono** で実装する（`apps/api`）
2. API の型は **Hono RPC** で共有する
   - サーバーのルート定義から `AppType` を export し（`@nowwhats/api/app`）、クライアントは `hc<AppType>()` で型付きクライアントを得る
   - 入力検証は zod（`@hono/zod-validator`）で行う
3. ルートはすべて `/api` 配下に置く。開発時は Vite の proxy で同一オリジンにし、CORS 設定を不要にする
4. 認証は `OwnerResolver` Port として切り出す。ステップ 3 では開発用の固定利用者を使い、`NODE_ENV=production` では起動できないようにする

## 検討した代替案

| 案                                | 不採用理由                                                                                                                                                        |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Python（FastAPI）で API を実装    | ドメインロジックを TypeScript と Python で二重実装することになり、同期時の再検証（ADR 0002）でずれが生じる。ツール類（lint・テスト・CI・依存管理）も 2 系統になる |
| OpenAPI（`@hono/zod-openapi` 等） | 言語非依存だが、現時点のクライアントはすべて TypeScript であり、導入パッケージと手順が増える                                                                      |

## 結果

- 良い点: サーバーの変更がクライアントの型エラーとして即座に検出される。追加の生成手順が不要
- 悪い点: TypeScript 以外のクライアントからは型の恩恵を受けられない
- 将来、Python 等が必要な処理（例: v2 の LLM 解析）が出た場合は、その部分だけを別サービスとし、`TaskDraftParser` Port（ADR 0004）の Adapter から呼び出す
- TypeScript 以外の利用者が出た場合は、OpenAPI の追加を別 ADR で検討する
