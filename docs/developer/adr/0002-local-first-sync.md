# 0002. ローカルファーストと自前の簡易同期

- ステータス: 提案
- 日付: 2026-10-05

## コンテキスト

- オフラインでもタスクの登録・編集・閲覧ができる必要がある
- 個人用のため、複数利用者による同時編集はない。ただし同一利用者の複数端末からの更新はあり得る
- ドメインルールはクライアント・サーバーの両方で同じコードによって検証したい（ADR 0001）

## 決定

1. **ローカル DB を正とするローカルファースト構成** とする
   - クライアントのローカル DB は SQLite に統一する
     - Web: WASM 版 SQLite（OPFS 永続化）
     - Mobile: expo-sqlite
     - Desktop: Tauri の SQLite プラグイン
2. **ID はクライアントで生成** する（UUIDv7）
3. **Outbox 方式で変更を送信** する
   - ユースケース実行時、集約の保存と同一トランザクションで Outbox に変更（ドメインイベント + 変更後の値 + 基準 version）を記録する
   - オンライン時に Outbox を順に push する
4. **サーバーは同じドメインコードで検証して反映** する
   - 検証 OK: 反映し、サーバー側の変更連番を採番する
   - 不変条件違反: `Rejection` として返し、クライアントはローカルを巻き戻して利用者に通知する
5. **pull はカーソル方式**
   - クライアントは `SyncCursor`（取得済みの変更連番）以降の差分をサーバーから取得し、ローカルに反映する
6. **競合解決は初期はフィールド単位の LWW（最後の書き込み優先）**
   - 集約に `version` を持たせ、基準 version とサーバーの version が異なる場合のみフィールド単位でマージする
   - 状態遷移の競合（例: 片方で完了、片方で中止）は、サーバーで遷移ルールを再適用し、不正なら差し戻す
7. **MVP 実装順** は、オンラインのみで縦の機能を一本通した後に同期を導入する。ただし、後からの大改修を避けるため、ID のクライアント生成と `version` は最初から実装する

## 検討した代替案

| 案                                                    | 不採用理由（現時点）                                                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 既製の同期エンジン（PowerSync、ElectricSQL、RxDB 等） | 開発速度は上がるが、データ操作がドメイン層を経由しなくなりやすく DDD と相性が悪い。自前同期で行き詰まった場合に再評価する |
| Firestore のオフライン SDK                            | ADR 0003 参照                                                                                                             |
| CRDT                                                  | 個人用途では競合が少なく、導入の複雑さに見合わない                                                                        |

## 結果

- 良い点: オフラインでもドメインルールが効く。同期ロジックを完全に制御できる
- 悪い点: 同期・競合解決・スキーマ移行（ローカル DB のマイグレーション）を自前で保守する必要がある
- 留意点: クライアントのローカル DB にも利用者データが残るため、ログアウト時のデータ消去方針を別途定める

## 要確認事項

- WASM 版 SQLite + OPFS の各ブラウザ対応状況は導入時に確認する
